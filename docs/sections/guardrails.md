# Guardrails: what the agent cannot do, and how we know

**No tool exists for sending, paying, approving or changing bank details.** The clerk can only *propose*: a draft is a row in the ledger in state `proposed`, addressed to the supplier's contact on file (the tool takes a supplier id, never an address). A draft that mentions bank details or payments is refused.

**Approval is enforced in code, at execution** (`domain/actions/ledger.py`). A draft carries a `payload_hash` (sha256 of its canonical payload). *Approve* takes the hash the person was shown and refuses a stale hash, a state other than `proposed`, or a row that no longer matches its recorded hash. *Execute* re-reads the row inside a transaction and sends (simulated) only if it is approved and unchanged; the outbox row is unique per action, so a second approval sends nothing. Attempted and confirmed times are recorded separately. Approve, reject and execute exist only as routes a person calls; no agent tool reaches them.

**One gate for every tool call** (`organism/gate.py`, a PreToolUse hook keyed by which agent is calling). It returns an explicit allow or deny (a silent hook is denied by the SDK's own permission check), enforces each agent's tool list, the item's delegation plan, foreground-only delegation, per-agent and per-tool call caps, and *no drafting for an untrusted sender*. Built-in tools are removed from every agent. Every decision, with its reason, is a run event shown on the run page and mirrored to the log.

**Untrusted text is data.** Trust is computed in code before any model reads a message. A message that fails (a look-alike domain, a free-mail reply-to, a change of bank details, an instruction aimed at software) is answered by code from the item's fields; no model reads it, so nothing in it can be followed or reversed. For mail that passes, the analyst reports an embedded instruction as a fact about the message, never as a task.

**The verifier is code, and the run cannot pass without it** (`organism/verifier.py`): every cited number came from a tool with the same value; every numeral in the text is one a tool returned; every day-and-month is a date a tool returned, and "today" is only the data date; required tools ran (the fire examines the shortage of every part the notice disrupts); every specialist in the plan handed off and Lookout read each handoff before writing; every draft is addressed to the contact on file and states no number or date a tool did not return; unknowns a tool raised are carried into the answer by code. A failed check sends Lookout back once; a revision that does worse is discarded. A reviewer's grade is advice shown beside the answer and never changes pass or fail.

**Generated code runs in a sandbox** (the Data steward): an AST allowlist (no file access, no `os`, no `getattr`), then a separate process with no network, writes only to a scratch directory, CPU and time limits, and OS-level read fencing on macOS; four attempts; the result is checked by code like a load gate; nothing is loaded without a person's approval.

**Bounded by construction.** Budgets per run (1 USD; 0.50 USD for a question), turn caps per agent, a cap on how many parts a run may examine, specialists never delegate (spawn depth 1), host settings and MCP config excluded (`setting_sources=[]`, `strict_mcp_config`).

**What breaks at 1000x the data and 100 customers, and what we would change.** Runs are in-process tasks with a SQLite file: they would move to a worker queue and Postgres, with one tenant key on every row and every tool. Services are computed on read from one database: the Action list and exposures would be precomputed on change. Tools return compact summaries today; at 1000x the parts they would be paginated and the plan caps would become budgets per customer. Each run starts a fresh SDK session (about 0.5 s) to keep runs independent; at volume a pool of warm sessions with per-run state reset would pay for itself. The verifier is the part that does not need to change.
